A task should be a **clear commitment to produce a specific, observable result**. The best format is complete enough that the owner can act without reopening the original conversation—but not so detailed that maintaining the task becomes a second task.

## The most complete practical task format

```text
TASK
[Action verb] + [specific object] + [important qualifier]

OUTCOME
Why this task matters and what result it should create.

DEFINITION OF DONE
The observable conditions that must be true for the task to be complete.

OWNER
One person accountable for completion.

DUE
The actual deadline, if one exists.

SCHEDULED
When the owner intends to work on it.

PRIORITY
How important it is relative to other work, and why.

NEXT ACTION
The first concrete physical or digital action required.

CONTEXT
Relevant background, decisions, constraints, and instructions.

INPUTS
Documents, links, files, data, people, or approvals needed.

DEPENDENCIES
What must happen before this can proceed.

EFFORT
Expected time, complexity, or task size.

STATUS
Not started / Ready / In progress / Blocked / In review / Done.

REVIEW OR FOLLOW-UP
When the task should be reconsidered if it is not completed.

TAGS
Project, area, client, location, skill, or work type.
```

## The title matters most

A strong task title begins with a verb and describes an observable action:

* **Draft the Q3 board update**
* **Call Maria to confirm the launch date**
* **Compare three payroll providers and recommend one**
* **Review the revised contract for termination risks**
* **Send the approved invoice to Acme Finance**

Weak task titles describe subjects rather than actions:

* Q3 board update
* Maria
* Payroll
* Contract
* Invoice

A useful formula is:

> **Verb + object + distinguishing detail**

For example:

> **Draft the Q3 board update using July financials**

The title should tell you what to do. The remaining fields should tell you why, how, when, and what “finished” means.

## The four essential fields

For most personal tasks, these are enough:

```text
Task:
Done when:
Due:
Context:
```

Example:

```text
Task:
Draft the Q3 board update using July financials.

Done when:
A 10-slide draft covering revenue, margin, hiring, risks, and next-quarter
priorities is shared with Dana for review.

Due:
August 24, 2026, 3:00 PM.

Context:
Use the approved board template. Financials are in the July close folder.
Keep the risk section candid but concise.
```

The **definition of done** is especially important. Without it, “work on presentation” can continue indefinitely. With it, everyone knows when the commitment has been fulfilled.

## A fully specified example

```text
TASK
Draft and circulate the Q3 board update.

OUTCOME
Give the board a clear view of performance, major risks, and the decisions
needed for Q4.

DEFINITION OF DONE
- 10–12 slides
- July actuals included
- Forecast compared with plan
- Three principal risks identified
- Q4 decisions listed explicitly
- Dana has reviewed the draft
- Final version sent to board members

OWNER
Alex

DUE
August 28, 2026, 5:00 PM

SCHEDULED
Draft: August 21
Internal review: August 24
Final revisions: August 27

PRIORITY
High—required for the August 31 board meeting.

NEXT ACTION
Duplicate the approved board template and insert the July financial tables.

CONTEXT
The board asked for more emphasis on cash efficiency and customer retention.
Avoid detailed departmental reporting unless it explains a material variance.

INPUTS
- July financial statements
- Retention analysis
- Hiring plan
- Approved board template

DEPENDENCIES
Finance must publish final July actuals by August 20.

EFFORT
Approximately 6 hours.

STATUS
Ready

REVIEW OR FOLLOW-UP
Escalate to the CFO on August 21 if final actuals have not been published.

TAGS
Board, Finance, Q3, Executive
```

## What each field solves

| Field              | Question it answers                     |
| ------------------ | --------------------------------------- |
| Task               | What exactly must be done?              |
| Outcome            | Why are we doing it?                    |
| Definition of done | How will we know it is finished?        |
| Owner              | Who is accountable?                     |
| Due                | When must the result exist?             |
| Scheduled          | When will the work happen?              |
| Priority           | What should win when work competes?     |
| Next action        | What should happen first?               |
| Context            | What does the owner need to know?       |
| Inputs             | What materials or access are required?  |
| Dependencies       | What could prevent progress?            |
| Effort             | How much capacity will it consume?      |
| Status             | Where is it in the workflow?            |
| Review date        | When should an inactive task resurface? |
| Tags               | How should it be grouped or retrieved?  |

## Important distinctions

### Due date versus scheduled date

These are not the same.

* **Due date:** The result is required by this time.
* **Scheduled date:** The owner intends to work on it at this time.
* **Start date:** Work should not begin before this time.
* **Review date:** Reconsider or inspect the task on this date.

Putting artificial deadlines on every task makes genuine deadlines harder to see. A task can be scheduled for Tuesday without being “due Tuesday.”

### Task versus project

A task should normally be completable through one coherent action or work session.

* **Task:** Send the signed agreement to the vendor.
* **Project:** Replace the company’s payroll system.

If completing the item requires several independently trackable actions, it is probably a project. Give the project an outcome and create separate tasks beneath it.

### Owner versus participants

A task can involve many people, but it should have **one accountable owner**. “Alex and Sam” often means neither person knows who is expected to close it.

Participants can be recorded separately:

```text
Owner: Alex
Contributors: Sam, Priya
Approver: Dana
```

### Priority versus urgency

Priority should represent the value of doing the work relative to other work. Urgency is about time pressure.

A useful classification is:

* **Critical:** Severe consequence if delayed.
* **High:** Material contribution to a current objective.
* **Normal:** Worth doing, but can yield to higher-value work.
* **Low:** Optional, opportunistic, or easily deferred.

Priority becomes more meaningful when accompanied by a reason:

```text
Priority: High—blocks customer onboarding.
```

## Qualities of a well-written task

A strong task is:

* **Actionable:** It begins with something the owner can do.
* **Specific:** It identifies the object, scope, and relevant qualifier.
* **Atomic:** It is not a disguised collection of unrelated actions.
* **Observable:** Completion can be verified.
* **Owned:** One person is accountable.
* **Contextualized:** Essential information is attached or linked.
* **Time-aware:** Real deadlines and scheduling information are distinguished.
* **Small enough:** It can move visibly through a workflow.

## Common task-writing failures

### “Work on…”

“Work on the pricing page” does not specify an outcome. Better:

> **Draft revised pricing-page copy for the three enterprise plans**

### “Finish…”

“Finish report” assumes everyone already understands the missing work. Better:

> **Incorporate Finance’s comments and submit the final expense report**

### Multiple actions hidden in one task

> Research vendors, select one, negotiate the contract, and migrate the data.

That is a project. Break it into milestones and tasks.

### No definition of done

“Review proposal” could mean skim, comment, approve, rewrite, or discuss. Better:

```text
Task:
Review the vendor proposal.

Done when:
Comments are added to the document and an approve/reject recommendation is
sent to Priya.
```

### Too much metadata

A task system can become bureaucratic when every two-minute action requires fifteen fields. Use the complete format as a **schema**, not as a requirement that every field be populated.

## A balanced default template

This is the format I would use for most professional work:

```text
TASK
[Verb] [specific object] [qualifier]

DONE WHEN
[Observable completion criteria]

OWNER
[One person]

DUE / SCHEDULED
[True deadline] / [planned work date]

PRIORITY
[Level] — [reason]

NEXT ACTION
[First concrete step]

CONTEXT
[Essential instructions, constraints, and links]

DEPENDENCIES
[Anything blocking or required]

STATUS
[Ready / In progress / Blocked / In review / Done]
```

The governing principle is:

> **The title should make the task actionable; the definition of done should make it finishable; the metadata should make it manageable.**
